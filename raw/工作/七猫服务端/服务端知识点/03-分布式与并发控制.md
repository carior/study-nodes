# 分布式、并发控制与数据一致性

## 1. 什么是分布式

分布式是指同一个系统由多台计算机、多个进程或多个独立服务共同完成工作。

单机系统：

```text
用户 -> 服务器 A -> MySQL
```

分布式系统：

```text
             -> 服务器 A
用户 -> 网关 -> 服务器 B -> MySQL / Redis
             -> 服务器 C
```

系统还可以按业务职责拆分：

```text
用户服务
订单服务
库存服务
支付服务
通知服务
```

### 为什么使用分布式

- 多台机器共同处理请求，提高处理能力
- 某个节点故障时其他节点继续工作，提高可用性
- 通过增加机器进行水平扩容
- 将复杂系统拆成职责清晰、可独立开发和部署的服务

### 分布式带来的问题

- 多个节点可能同时修改同一份数据
- 网络可能超时或中断
- 节点可能突然宕机
- 不同节点看到的数据可能暂时不一致
- 同一请求或消息可能被重复处理
- 跨服务操作很难同时成功或同时失败

## 2. 服务为什么部署多个实例

服务是一套业务能力和代码；实例是这套代码的一次实际运行。

```text
订单服务
├── 订单实例 A
├── 订单实例 B
└── 订单实例 C
```

部署多个实例可以：

- 并行处理更多请求
- 避免单点故障
- 支持水平扩缩容
- 支持滚动发布和不停机升级

业务实例通常尽量设计为无状态。登录状态、业务数据和文件分别放在 Redis、MySQL 和对象存储等共享设施中，使任意实例都能处理请求。

## 3. 普通锁和分布式锁

### 普通进程锁

Go 的互斥锁可以协调同一进程内的 goroutine：

```go
var mu sync.Mutex

mu.Lock()
defer mu.Unlock()

count++
```

但服务器 A 和服务器 B 各自拥有独立内存，A 的 `sync.Mutex` 无法阻止 B 操作同一份数据库数据。

### 分布式锁

分布式锁是所有服务实例都能识别的公共锁，通常借助 Redis、etcd、ZooKeeper 或数据库实现：

```text
实例 A ─┐
实例 B ─┼-> 公共分布式锁
实例 C ─┘
```

例如每天只生成一次报表，但报表服务有三个实例。三个实例先竞争：

```text
lock:daily-report:2026-08-19
```

只有获得锁的实例执行任务。

Redis 的基础加锁命令：

```redis
SET lock:product:1001 request-abc NX EX 10
```

- `NX`：只有 Key 不存在时设置成功。
- `EX 10`：10 秒后自动过期，防止持有锁的实例宕机后永远不释放。
- `request-abc`：锁持有者的唯一标识。

释放时必须确认锁仍属于自己，并通过 Lua 脚本保证“检查和删除”是原子操作：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

分布式锁实现复杂，实际项目应优先使用成熟库。如果数据库条件更新或唯一索引能够解决问题，通常优先使用更简单的方案。

## 4. 数据库事务

事务把多个数据库操作视为一个整体：要么全部成功，要么全部失败。

例如 A 向 B 转账 100 元：

```sql
BEGIN;

UPDATE account
SET balance = balance - 100
WHERE id = 1;

UPDATE account
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

中途发生错误时执行：

```sql
ROLLBACK;
```

数据库会撤销本次事务中的修改，避免只扣款但没有入账。

## 5. 唯一索引

唯一索引保证某个字段或字段组合不能重复：

```sql
CREATE UNIQUE INDEX uk_payment_no
ON payments(payment_no);
```

即使两个服务实例同时插入相同的支付流水号，也只能有一个成功。唯一索引经常作为防止重复数据的最后一道防线。

## 6. 条件更新

条件更新把业务条件直接写进 SQL：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 1001
  AND stock > 0;
```

如果库存只剩一件，两个请求同时执行时，通常只有一个请求影响 1 行；另一个请求发现库存已为 0，影响 0 行。应用根据受影响行数判断是否成功。

这通常比“先查库存，再修改库存”更可靠，因为查询和更新之间的数据可能被其他请求改变。

## 7. 乐观锁

乐观锁假设冲突不经常发生，所以不提前锁住数据，而是在更新时检查数据有没有被修改。

读取到的数据：

```text
商品 1001
stock = 10
version = 5
```

更新时带上原版本号：

```sql
UPDATE products
SET stock = 9,
    version = version + 1
WHERE id = 1001
  AND version = 5;
```

如果别人已经修改过商品，`version` 就不再是 5，此次更新影响 0 行。应用可以重新读取后重试，或者返回冲突。

## 8. 悲观锁

悲观锁认为数据很可能发生冲突，因此先锁住数据，再进行操作。MySQL 中常见写法是事务配合 `SELECT ... FOR UPDATE`：

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 1001
FOR UPDATE;

UPDATE products
SET stock = stock - 1
WHERE id = 1001;

COMMIT;
```

第一个事务锁住记录后，其他事务通常需要等待它提交或回滚。

| 对比 | 悲观锁 | 乐观锁 |
|---|---|---|
| 思路 | 先锁住再操作 | 更新时检查冲突 |
| 常见实现 | `SELECT ... FOR UPDATE` | `version` 条件更新 |
| 冲突时 | 其他事务等待 | 更新失败后重试 |
| 适合场景 | 冲突频繁、操作较短 | 冲突较少、读取较多 |
| 主要风险 | 等待、超时、死锁 | 高冲突时频繁重试 |

数据库悲观锁通常协调同一数据库中的事务；分布式锁可以协调多个进程对任务、文件或其他共享资源的操作。

## 9. 请求幂等

幂等是指同一个请求执行一次和执行多次，最终业务效果相同。

例如支付请求由于响应丢失被客户端重试三次，系统不能扣款三次。客户端可以携带唯一幂等键：

```http
POST /payments
Idempotency-Key: PAY-20260819-10001
```

服务端处理流程：

```text
1. 检查幂等键是否已经处理
2. 未处理：执行业务并保存处理结果
3. 已处理：直接返回第一次的处理结果
```

可以通过数据库唯一索引保证幂等键不会重复插入。幂等不是简单拒绝重复请求，而是确保重复请求不会产生重复副作用。

## 10. 如何选择并发控制方案

没有一种锁适合所有问题，可以优先按复杂度选择：

1. 能用单条条件 SQL 完成时，优先使用条件更新。
2. 需要防止重复数据时，使用唯一索引兜底。
3. 冲突较少时，可以使用乐观锁。
4. 同一数据库事务内冲突频繁时，可以考虑悲观锁。
5. 必须协调不同机器、不同进程或数据库之外的资源时，再考虑分布式锁。
6. 面对请求重试和消息重复投递时，业务必须设计幂等。
