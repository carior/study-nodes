# 网关、负载均衡与服务实例

## 1. 什么是网关

网关是系统统一对外的入口。客户端通常不直接访问后面的每一个服务，而是先访问网关，再由网关转发给正确的服务。
“网关层”指的是 **HTTP 接口入口层**，也就是把浏览器发来的 HTTP 请求转换成后端方法调用的这一层。

```text
                         -> 用户服务
客户端 -> API 网关       -> 订单服务
                         -> 支付服务
                         -> 小说服务
```

网关根据请求路径路由：

```text
/api/users/*    -> 用户服务
/api/orders/*   -> 订单服务
/api/payments/* -> 支付服务
/api/books/*    -> 小说服务
```

### 网关的常见功能

- 请求路由
- 负载均衡
- 身份认证
- 限流
- 统一日志和监控
- HTTPS 证书处理
- CORS 跨域处理
- 请求头和协议转换

网关适合承载通用能力，不应放入计算商品价格、退款、优惠券判断等具体业务逻辑。

## 2. 什么是负载均衡

负载均衡把不同请求分配给多个服务实例，避免流量集中在一台服务器上：

```text
                  -> 小说实例 A
用户请求 -> 网关 -> 小说实例 B
                  -> 小说实例 C
```

负载均衡不是把一个请求拆成三份，而是把不同请求分配给不同实例。

### 为什么需要负载均衡

- 多个实例并行处理，提高吞吐量
- 某个实例故障时将请求转移到正常实例
- 支持增加或减少实例
- 支持滚动发布

### 常见算法

- 轮询：A、B、C、A 依次分配
- 随机：随机选择实例
- 最少连接：选择当前连接数最少的实例
- 加权：性能更强的实例承担更多流量
- 一致性哈希：根据用户 ID 或资源 ID 选择相对固定的节点

### 健康检查

负载均衡器会持续访问实例的健康检查接口：

```http
GET /health
```

实例连续检查失败后会被移出可用列表，恢复后再重新加入。

## 3. 服务和实例的区别

- 服务是一套业务能力和代码，例如订单服务。
- 实例是这套服务代码正在运行的一个进程或副本。

```text
订单服务
├── 实例 A：10.0.1.11:8080
├── 实例 B：10.0.1.12:8080
└── 实例 C：10.0.1.13:8080
```

银行类比：服务是“办理个人开户”，实例是多个能够办理个人开户的窗口。

## 4. Nginx upstream 中是什么地址

传统部署中的配置：

```nginx
upstream order_service {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    server 10.0.1.13:8080;
}
```

这里通常配置的是订单服务后端实例地址：

```text
10.0.1.11:8080 -> 订单实例 A
10.0.1.12:8080 -> 订单实例 B
10.0.1.13:8080 -> 订单实例 C
```

- IP 是实例所在服务器或容器的内网地址。
- 端口是订单程序监听的端口。
- `order_service` 是 Nginx 为这组实例定义的名字。

完整示例：

```nginx
upstream order_service {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    server 10.0.1.13:8080;
}

server {
    listen 80;
    server_name test-1.example.com;

    location /api/orders/ {
        proxy_pass http://order_service;
    }
}
```

请求链路：

```text
客户端请求 test-1.example.com/api/orders/1001
  |
  v
Nginx 网关
  |
  v
订单实例 A / B / C
```

## 5. 测试环境地址、网关地址和实例地址

| 地址类型 | 示例 | 含义 |
|---|---|---|
| 测试环境域名 | `test-1.example.com` | 客户端访问整套环境的入口 |
| 云负载均衡地址 | 公网 IP 或云平台地址 | 将流量分发给多个网关 |
| 网关地址 | `10.0.1.11:80` | Nginx 等网关程序监听的地址 |
| 实例地址 | `10.0.1.12:8080` | 真正执行业务代码的进程地址 |

三个测试环境通常是三套隔离系统，而不是三个实例：

```text
test-1 -> test-1 网关 -> test-1 服务和数据库
test-2 -> test-2 网关 -> test-2 服务和数据库
test-3 -> test-3 网关 -> test-3 服务和数据库
```

不要把三套测试环境直接配置成同一个 `upstream`，否则请求可能进入错误环境并造成数据混用。

## 6. 网关地址如何形成

网关地址也是普通的 `IP + 端口`：

```text
网关所在服务器的 IP + 网关程序监听端口
```

例如：

```text
服务器内网 IP：10.0.1.11
Nginx 监听端口：80
网关内网地址：http://10.0.1.11:80
```

Nginx 只配置监听端口：

```nginx
server {
    listen 80;
}
```

服务器 IP 不是 Nginx 产生的，而是由阿里云、公司网络管理员、DHCP 或静态网络配置分配的。

网关地址和实例地址看起来相似，是因为它们都采用 `IP:端口` 格式。区别在于该地址运行的程序和承担的职责。

## 7. 三台服务器的部署示例

### 方案一：一台网关，两台业务服务器

```text
服务器 1：10.0.1.11
└── Nginx 网关：80

服务器 2：10.0.1.12
└── 订单实例 A：8080

服务器 3：10.0.1.13
└── 订单实例 B：8080
```

```nginx
upstream order_service {
    server 10.0.1.12:8080;
    server 10.0.1.13:8080;
}
```

此方案的 Nginx 是单点：网关所在服务器宕机后，后端实例即使正常，用户也无法访问。

### 方案二：每台服务器都运行网关和业务实例

```text
服务器 1：10.0.1.11
├── Nginx：80
└── 订单实例 A：8080

服务器 2：10.0.1.12
├── Nginx：80
└── 订单实例 B：8080

服务器 3：10.0.1.13
├── Nginx：80
└── 订单实例 C：8080
```

一个 IP 可以运行多个程序，只要监听不同端口：

```text
10.0.1.11:80   -> Nginx
10.0.1.11:8080 -> 订单服务
10.0.1.11:6379 -> Redis
```

多个 Nginx 前面通常还会放置云负载均衡：

```text
                       -> Nginx A
用户 -> 云负载均衡入口 -> Nginx B
                       -> Nginx C
```

## 8. 网关如何知道选择哪个实例

首先需要获得可用实例列表，常见方式包括：

- 在 Nginx `upstream` 中静态配置
- 从 Nacos、Consul 等注册中心动态发现
- 通过 Kubernetes Service 自动发现 Pod

获得列表后，网关按照轮询、随机、最少连接或权重等规则选择，并通过健康检查排除故障实例。

## 9. 滚动发布时为什么允许新旧版本同时存在

滚动发布期间确实可能出现：

```text
请求 1 -> 旧版本
请求 2 -> 新版本
```

因此发布必须保证新旧版本在过渡期兼容。通常按照以下步骤：

```text
1. 数据库和接口先兼容新旧版本
2. 部署少量新实例
3. 观察错误率、响应时间和业务指标
4. 逐步替换旧实例
5. 全部稳定后清理旧逻辑
```

旧实例下线时，应先停止接收新请求，等待正在处理的请求结束后再关闭，这叫优雅下线。

对于不兼容变更，可以使用：

- 灰度发布：少量用户先进入新版本
- 蓝绿发布：准备完整新环境，验证后整体切换
- API 版本化：同时维护 `/api/v1` 和 `/api/v2`
